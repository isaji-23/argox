# Argox Processor Development Guide

This guide provides a comprehensive technical blueprint for developers who want to write custom in-flight data transformation components (processors) for the Argox SDK. It covers the `ArgoxProcessor` contract, lifecycle execution phases, error-handling and fail-open semantics, performance patterns, telemetry events, and testing best practices, along with a complete reference implementation.

---

## 1. Introduction to Processors in Argox

In Argox, an **ArgoxProcessor** is an extensible component designed to transform agent data in real-time ("in-flight") during the agent's execution lifecycle. Processors run on the hot execution path, intercepting and modifying prompts, tool arguments, and model responses before they reach their next destination (the LLM, the tool execution body, or the end user).

### Key Architectural Difference
It is critical to distinguish `ArgoxProcessor` from OpenTelemetry's `SpanProcessor`:
* **OTel SpanProcessor**: Transforms, filters, or exports *telemetry data* (spans) asynchronously after they are emitted.
* **ArgoxProcessor**: Transforms *actual agent execution data* synchronously, altering the inputs and outputs of the LLM or tools in real-time.

### Primary Use Cases
* **PII Redaction**: Removing or masking credit cards, social security numbers, IBANs, or phone numbers before data is sent to external LLM providers (preserving data sovereignty).
* **Secrets Sanitization**: Detecting and redacting API keys, database connection strings, or passwords from tool arguments or outputs.
* **Constraint Validation**: Validating LLM outputs against specific schemas and raising exceptions if they violate compliance rules.
* **Format Normalization**: Modifying prompt formatting or response structures to match internal enterprise schemas.

---

## 2. The `ArgoxProcessor` Interface

Every custom processor must subclass the abstract base class `ArgoxProcessor` (defined in `argox.interfaces.processor.py`). The interface defines three asynchronous methods, representing the three transformation points in an agent run:

```python
from abc import ABC, abstractmethod
from argox.core.context import RunContext

class ArgoxProcessor(ABC):

    @abstractmethod
    async def process_input(self, text: str, ctx: RunContext) -> str:
        """
        Transforms the user prompt before sending it to the LLM.
        """
        pass

    @abstractmethod
    async def process_tool_args(self, tool_name: str, args: dict, ctx: RunContext) -> dict:
        """
        Transforms or validates tool call arguments before tool execution.
        """
        pass

    @abstractmethod
    async def process_output(self, text: str, ctx: RunContext) -> str:
        """
        Transforms, cleans, or audits the LLM response before returning to the user.
        """
        pass
```

### The `RunContext` Parameter
Each method receives a `RunContext` object, which provides metadata about the current execution:
* `ctx.run_id`: A unique string identifier for the active run.
* `ctx.agent_name`: The name of the agent being monitored.
* `ctx.metadata`: A dictionary of custom attributes or context variables passed to the run.

## 3. Lifecycle Execution and Pipeline Mechanics

Processors are registered with the `ArgoxManager` (or via the `@argox.monitor` decorator) and are executed sequentially in the order they were registered:

```python
manager.register_processor(pii_redactor, strict=False)
manager.register_processor(secret_sanitizer, strict=True)
```

During a monitored run (`ArgoxManager.run`), the execution occurs at three distinct phases:

1. **Input Phase (`process_input`)**:
   - Executes after the raw prompt is received and persisted in metrics, but before input policy evaluation.
   - Ideal for redacting sensitive user queries before the LLM can process them.
2. **Tool Arguments Phase (`process_tool_args`)**:
   - Intercepted by the framework plugin during tool invocation.
   - Executes before the tool body runs. The original, raw arguments never reach the tool.
3. **Output Phase (`process_output`)**:
   - Executes after the LLM returns its response, but before output policy evaluation.
   - Ensures that sensitive data generated by the LLM or returned by tools is redacted before reaching the end user.

---

## 4. Key Design Patterns and Requirements

### A. Fail-Open vs. Strict Semantics
When registering a processor, you must specify its strictness level (`strict=True` or `strict=False`):

* **Fail-Open Mode (`strict=False`, Default)**:
  - If the processor raises an exception during execution (e.g., a regex engine error or an external API timeout), the `ArgoxManager` **captures the error**, records it as an OTel span event, and **continues the pipeline**.
  - The *unmodified* data from before the failed processor is forwarded to the next processor in the chain. This prevents a minor processor failure from crashing the entire agent run.
* **Strict Mode (`strict=True`)**:
  - If the processor raises an exception, the `ArgoxManager` immediately **aborts the run**, marks the active OTel span status as `ERROR`, and propagates the exception (typically raising `PermissionError` or the original exception) to the caller.
  - Use `strict=True` for critical compliance requirements (e.g., if you *must* guarantee that no PII ever leaves the boundary, a failure in the PII redactor should block the run entirely).

### B. Tool Arguments Deep Copying
To prevent a fail-open processor from corrupting the tool arguments in case of a partial failure, the `ArgoxManager` passes a **deep copy** of the arguments dictionary (`copy.deepcopy(args)`) to `process_tool_args`.
* The returned, mutated dictionary is only accepted and forwarded if the processor completes **successfully**.
* If a processor fails in fail-open mode, its partial changes are discarded, and the original arguments are passed to the next processor.

### C. Asyncio Cancellation Propagation
`asyncio.CancelledError` is a control-flow exception used by the event loop to shut down tasks cleanly.
* **Rule**: Your processor **must never** suppress `asyncio.CancelledError` in `try/except` blocks. If caught, you must re-raise it immediately.
* The `ArgoxManager` explicitly lets `CancelledError` propagate out of the pipeline, regardless of the `strict` flag.

### D. Performance Patterns
Because processors run synchronously on the agent's hot execution path, latency is a critical concern:
1. **Prefer Local Operations**: Use highly optimized local regex, rules, or caches rather than blocking network calls where possible.
2. **Handle Network Timeouts**: If you must call an external API (e.g., a hosted PII detection service), always enforce a strict, low timeout (e.g., <500ms) and design a graceful fallback.
3. **Avoid Unnecessary Copying**: Do not perform extra deep copies inside your processor; the Manager already deep-copies tool arguments before passing them to `process_tool_args`.

## 5. Telemetry and Span Events

The `ArgoxManager` automatically instruments the execution of processors, writing details directly to the active OTel run span:

1. **On Successful Application**:
   - Emits a span event named `argox.processor.applied`.
   - Attributes:
     - `argox.processor.name`: The class name of the processor.
     - `argox.processor.phase`: The active phase (`input`, `tool_args`, or `output`).
2. **On Failure (Exception Raised)**:
   - Emits a span event named `argox.processor.error`.
   - Attributes:
     - `argox.processor.name`: The class name of the processor.
     - `argox.processor.phase`: The active phase.
     - `argox.processor.strict`: A boolean indicating if strict mode was enabled.
     - `exception.type`: The exception class name.
     - `exception.message`: The string representation of the exception.
     - `argox.processor.tool_name`: (Only in `tool_args` phase) The name of the tool being called.

---

## 6. Testing Your Processors

When writing unit tests for your custom processors, ensure you cover:
1. **Transformation Accuracy**: Verify that the input, tool arguments, and output are transformed correctly under normal conditions.
2. **Fail-Open Behavior**: Mock a failure in the processor and assert that when `strict=False`, the run continues and the unmodified data is returned.
3. **Strict Behavior**: Mock a failure and assert that when `strict=True`, the exception propagates and blocks the run.
4. **Cancellation Propagation**: Verify that `asyncio.CancelledError` is propagated cleanly.

## 7. Reference Implementation

Below is a complete, self-contained reference implementation of a custom processor that redacts credit cards and API keys from prompts, tool arguments, and outputs, along with a comprehensive test suite.

### A. The Custom Processor (`redactor_processor.py`)
```python
# redactor_processor.py
import re
import asyncio
from typing import Any
from argox.interfaces.processor import ArgoxProcessor
from argox.core.context import RunContext

class RedactorProcessor(ArgoxProcessor):
    """
    A custom ArgoxProcessor that redacts Credit Card numbers (VISA/Mastercard)
    and sensitive API keys (e.g., 'sk-...') from all text and tool arguments.
    """
    
    # Regex for Credit Cards (16 digits with optional hyphens/spaces)
    CC_REGEX = re.compile(r'\b(?:\d[ -]*?){13,16}\b')
    # Regex for generic API keys (e.g., secret keys starting with sk- followed by alphanumeric)
    API_KEY_REGEX = re.compile(r'\bsk-[a-zA-Z0-9]{24,40}\b')

    def _redact_text(self, text: str) -> str:
        if not text:
            return text
        text = self.CC_REGEX.sub("[REDACTED_CREDIT_CARD]", text)
        text = self.API_KEY_REGEX.sub("[REDACTED_API_KEY]", text)
        return text

    async def process_input(self, text: str, ctx: RunContext) -> str:
        # Redact the user prompt before sending it to the LLM
        return self._redact_text(text)

    async def process_tool_args(self, tool_name: str, args: dict, ctx: RunContext) -> dict:
        # Redact credit cards or secrets nested inside tool arguments
        redacted_args = {}
        for key, value in args.items():
            if isinstance(value, str):
                redacted_args[key] = self._redact_text(value)
            elif isinstance(value, dict):
                # Recursively redact sub-dictionaries
                redacted_args[key] = await self.process_tool_args(tool_name, value, ctx)
            else:
                redacted_args[key] = value
        return redacted_args

    async def process_output(self, text: str, ctx: RunContext) -> str:
        # Redact the LLM output before returning it to the user
        # In case the model echoed a secret or a credit card
        return self._redact_text(text)
```

### B. The Test Suite (`test_processor.py`)
```python
# test_processor.py
import asyncio
import pytest
from unittest.mock import MagicMock

from argox.core.context import RunContext
from .redactor_processor import RedactorProcessor

@pytest.fixture
def mock_context():
    return RunContext(run_id="run-999", agent_name="test-governance-agent", metadata={})

@pytest.mark.asyncio
async def test_redactor_processor_input_phase(mock_context):
    processor = RedactorProcessor()
    
    raw_prompt = "Hello, my card is 4111 1111 1111 1111 and my key is sk-1234567890abcdef1234567890."
    expected = "Hello, my card is [REDACTED_CREDIT_CARD] and my key is [REDACTED_API_KEY]."
    
    result = await processor.process_input(raw_prompt, mock_context)
    assert result == expected

@pytest.mark.asyncio
async def test_redactor_processor_tool_args_phase(mock_context):
    processor = RedactorProcessor()
    
    raw_args = {
        "payment_method": "credit_card",
        "card_number": "1234-5678-1234-5678",
        "nested_config": {
            "api_endpoint": "https://api.provider.com",
            "token": "sk-abcdef1234567890abcdef123456"
        },
        "amount": 150.0
    }
    
    expected = {
        "payment_method": "credit_card",
        "card_number": "[REDACTED_CREDIT_CARD]",
        "nested_config": {
            "api_endpoint": "https://api.provider.com",
            "token": "[REDACTED_API_KEY]"
        },
        "amount": 150.0
    }
    
    result = await processor.process_tool_args("process_payment", raw_args, mock_context)
    assert result == expected

@pytest.mark.asyncio
async def test_redactor_processor_output_phase(mock_context):
    processor = RedactorProcessor()
    
    raw_output = "Sure, I have stored your key: sk-abcdef1234567890abcdef123456."
    expected = "Sure, I have stored your key: [REDACTED_API_KEY]."
    
    result = await processor.process_output(raw_output, mock_context)
    assert result == expected

@pytest.mark.asyncio
async def test_processor_cancellation_propagation(mock_context):
    class FailingProcessor(RedactorProcessor):
        async def process_input(self, text: str, ctx: RunContext) -> str:
            raise asyncio.CancelledError()

    processor = FailingProcessor()
    
    # Cancellation must propagate and never be caught by try/except blocks inside processors
    with pytest.raises(asyncio.CancelledError):
        await processor.process_input("test", mock_context)
```
