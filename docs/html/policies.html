01Anatomía de una política

Una política es un documento YAML con un id, una versión y una lista de reglas. Cada regla tiene un trigger (cuándo se evalúa), una condición (qué comprueba) y una acción (qué hacer si se cumple).

02Tres triggers, una métrica cada uno

El trigger marca en qué momento del run se evalúa la regla, y cada uno expone exactamente una métrica string:

TriggerMomentoMétricaMétodo del cliente
on_inputAntes de enviar el prompt al LLMpromptcheck_input()
on_tool_callAntes de exponer cada tooltool_nameis_tool_allowed()
on_outputTras recibir la respuesta del LLMoutputcheck_output()
Cuidado con tipos. En la v1 las tres métricas son strings. Un threshold numérico con gt/lt sobre prompt/output/tool_name no disparará. Los operadores numéricos existen para métricas futuras.

03Ocho operadores

Con a = valor de la métrica y b = threshold (implementación exacta de operator_funcs en parser.py):

OperadorSemánticaImplementación
eqIgualdada == b
neqDesigualdada != b
gtMayor quea > b
gteMayor o iguala >= b
ltMenor quea < b
lteMenor o iguala <= b
containsContenciónb in a (si a es list/str/dict)
inPertenenciaa in b (si b es list/set/tuple)
Métrica ausente → False. Si la métrica no está en el diccionario, el predicado devuelve False (la regla no dispara). Es fail-open a nivel de métrica ausente.

04Tres acciones

block detiene la ejecución o quita la tool alert continúa pero queda registrado ok no-op, se ignora

Toda evaluación devuelve un PolicyResult inmutable (passed, reason, rule_id). Solo block tiene passed=False; un alert pasa pero lleva rule_id, por eso se distingue de un ok puro.

07Cliente Local vs Remote

Ambos delegan la evaluación en el mismo PolicyCache síncrono. Difieren en de dónde sacan las políticas y en su resiliencia:

AspectoLocalPolicyClientRemotePolicyClient
FuenteArchivo YAML de discoEndpoint /policies/bundle del Collector
CargaUna vez en __init__Polling en background (~60 s)
Hot-pathcache.evaluate(...) — cero red en ambos
Error de evaluaciónFail-closed → blockFail-closed → block

08Ejemplo comentado

id: guardrails
version: 1
status: active
rules:
  # input: bloquea intento de SQL injection
  - id: GR-IN-01
    trigger: on_input
    condition: { metric: prompt, operator: contains, threshold: "drop table" }
    action: block
  # input: menciona credenciales → solo alerta
  - id: GR-IN-02
    trigger: on_input
    condition: { metric: prompt, operator: contains, threshold: password }
    action: alert
  # tool: acceso a secretos → quita la tool
  - id: GR-TOOL-01
    trigger: on_tool_call
    condition: { metric: tool_name, operator: eq, threshold: get_secret }
    action: block
  # output: stack trace filtrado → block
  - id: GR-OUT-01
    trigger: on_output
    condition: { metric: output, operator: contains, threshold: STACK_TRACE }
    action: block
