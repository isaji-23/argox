01What gets deployed

Argox is a two-service stack. The Collector ingests OpenTelemetry traces, stores span payloads in Azure Blob Storage, and keeps a query index in an embedded DuckDB file. The Dashboard is a static single-page app served by nginx, which also reverse-proxies the API so the browser stays same-origin.

On Azure both run as Azure Container Apps in one environment. The Dashboard is the only public endpoint; the Collector runs on internal ingress and is reachable only from inside the environment. Authentication (COL-09) is enabled — every endpoint except the health probes requires a bearer credential.

Two files, two jobs. This page is the conceptual reference. For the exact, ordered commands, follow azure-deploy-steps.md in this folder.

04Storage & the DuckDB persistent volume

Argox writes to two kinds of storage, and they are deliberately different:

Blob Storage — span payloads

The Collector streams trace batches and policy blobs into the argox container via a connection string. This is durable object storage; nothing special is needed beyond the account.

Azure Files — DuckDB index

The query index is a single DuckDB file at /data/index.duckdb. A container's local disk is ephemeral, so the file must live on a mounted Azure Files share to survive restarts and new revisions.

How the volume is created and mounted

Mounting Azure Files on a Container App is a three-part move: create the share, register it with the environment, then reference it from the Collector app's template.

① Create the share (5 GiB is generous for an index):

az storage share-rm create -g $RG --storage-account $STORAGE \
  -n argox-index --quota 5

② Register it with the ACA environment — this names the storage so apps can mount it (SMB, no VNet required):

az containerapp env storage set -g $RG -n $ENV \
  --storage-name argox-index \
  --storage-type AzureFile \
  --azure-file-account-name $STORAGE \
  --azure-file-account-key $STG_KEY \
  --azure-file-share-name argox-index \
  --access-mode ReadWrite

③ Mount it on the Collector by editing the app YAML (there is no single CLI flag for this):

# az containerapp show -n collector -g $RG -o yaml > collector.yaml
    template:
      containers:
      - name: collector
        # ...
        volumeMounts:
        - volumeName: index-vol
          mountPath: /data          # ARGOX_INDEX_DUCKDB_PATH lives here
      volumes:
      - name: index-vol
        storageName: argox-index    # the env storage from ②
        storageType: AzureFile
# az containerapp update -n collector -g $RG --yaml collector.yaml
Single writer only. DuckDB allows exactly one writer. The Collector must run with --min-replicas 1 --max-replicas 1. Raising the replica count puts concurrent writers on the same shared file and will corrupt the index. Multi-replica indexing is tracked as COL-15.
Verify it persists. After some traffic, az containerapp exec -n collector -g $RG --command "ls -la /data" should show index.duckdb — and it should still be there after deploying a new revision.

05Configuration

All Collector settings are ARGOX_* environment variables. Secrets (connection string, admin key) are stored as Container App secrets and referenced with secretref:.

Managed Identity is not supported yet. The storage backend only authenticates via from_connection_string. Until it learns DefaultAzureCredential, the connection string (kept as a secret) is the only path to Blob Storage.

06Deploy flow at a glance

  1. Prereqs — az login, add the containerapp extension, register providers.
  2. Resource group in your region.
  3. Registry + images — az acr build the Collector and Dashboard.
  4. Storage — account, blob container argox, file share argox-index.
  5. ACA environment + register the Files share with it.
  6. Collector app — internal ingress, 1 replica, secrets, then mount /data.
  7. Dashboard app — external ingress, set COLLECTOR_UPSTREAM.
  8. Smoke test — mint a key, ingest the seed trace, open the public URL.

Each step is a runnable command in azure-deploy-steps.md.

07Updating after changes

Container Apps is revision-based: every change creates a new immutable revision and traffic shifts to it once healthy. Mounts, secrets and env vars belong to the app template, so they carry over — you only re-specify what changed. Always push a fresh tag (never reuse latest) so revisions and rollbacks stay traceable.

Code change

Rebuild the image with a new tag, then az containerapp update --image …:v2. Rolls a new revision.

Config / secret

--set-env-vars or secret set + an update to bump a revision. No rebuild needed.

Volume / template

Re-export YAML, edit, update --yaml.

Rollback

Re-deploy the previous tag: update --image …:v1. Immutable tags make this trivial.

# Code change: rebuild + roll
az acr build -r $ACR -t argox-collector:v2 ../../argox-project/argox-collector
az containerapp update -n collector -g $RG --image $ACR.azurecr.io/argox-collector:v2
DuckDB during the swap. The new Collector replica starts while the old one may still run, so two processes can briefly hold the same DuckDB file. The file lock serializes them (the new one retries until the old revision is gone). For a clean swap, deactivate the old revision first: az containerapp revision deactivate -n collector -g $RG --revision <old>. The Dashboard is stateless and updates with zero downtime.

08Security checklist

✔Collector on internal ingress — never expose the API publicly; it has no rate limiting.
✔Auth on (ARGOX_AUTH_ENABLED=true); rotate the bootstrap admin key after minting real keys.
✔Secrets via Container App secrets / Key Vault references — never as literal env values.
✔TLS is automatic on the external Dashboard ingress.
✔Dashboard SSO via Entra ID (optional) for human users; API keys for machine ingest.
